# Windows 后台日志导致 CSV 重导入失败：修复设计

## 背景与根因

用户将工具导出的 `cleaned_data_*.csv` 重新上传后，接口返回：

```text
Error reading file cleaned_data_20260805_160000.csv: [Errno 22] Invalid argument
```

使用同名、同字段结构的最小 CSV 可以在当前服务器稳定复现该错误；相同字节交给同一版本的 pandas 在独立进程中可以正常解析。失败发生在 CSV 解析分支中的控制台输出调用。Windows 后台启动方式留下了不可用的标准输出句柄，`print(..., flush=True)` 抛出 `OSError(22)`，随后被上传路由的宽泛异常处理误报为文件读取失败。

因此，问题与 CSV 内容、文件名或 DeepSeek API 无关。根因是诊断日志异常穿透了业务流程。

## 目标

- 工具导出的 CSV 可以重新上传并进入筛选流程。
- 标准输出已关闭或不可写时，日志失败不得中断文件解析或后台筛选。
- 真正的文件读取、格式检测和 CSV 解析错误仍按现有方式返回。
- 保持现有 CSV 字段映射、筛选逻辑和 API 调用行为不变。

## 非目标

- 不重写 CSV 自动检测算法。
- 不重构全部日志为完整的日志平台。
- 不改变导出文件格式或下载文件名。
- 不吞掉除日志输出故障之外的业务异常。

## 方案

### 安全控制台日志

在应用模块中增加一个小型安全日志边界：

- 保存原始 `print` 调用。
- 模块内现有诊断输出统一经过安全包装。
- 仅捕获标准输出常见的 `OSError` 和已关闭流导致的 `ValueError`。
- 其他编程错误不捕获，避免隐藏真实缺陷。

这样无需大规模修改现有诊断信息，也能保证日志通道与业务处理隔离。

### Windows 后台启动

重启当前服务时使用 Windows 原生的标准输出和标准错误文件重定向，避免产生无效句柄。代码级安全边界仍然保留，因为应用不应依赖特定启动命令才能正确处理文件。

## 数据流

1. 浏览器通过 `/screen` 上传一个或多个文件。
2. CSV 内容仍读取到内存并使用现有编码和分隔符策略解析。
3. 格式检测和进度诊断经过安全日志边界。
4. 如果日志目标不可写，仅丢弃该条诊断输出。
5. 文件解析成功后继续创建筛选任务；如果解析本身失败，仍返回相应的 400 错误。

## 错误处理

- 安全日志只吸收 `OSError` 和 `ValueError`，不改变路由的业务错误处理。
- 不在安全日志中递归尝试写入另一个可能失效的控制台流。
- API 密钥、文献正文等敏感内容不会新增到日志中。

## 测试设计

### 回归测试

新增集成测试，模拟模块的底层控制台输出抛出 `OSError(22, "Invalid argument")`，再上传工具导出格式的最小 CSV。修复前应返回 400 并复现原错误；修复后应成功创建筛选任务。

### 保留错误行为

验证真正无法解析的文件仍返回 400，确保安全日志没有掩盖解析错误。

### 完整验证

- 运行新增回归测试并确认先红后绿。
- 运行完整 unittest 套件。
- 执行 Python 编译检查和 `git diff --check`。
- 重启本地服务。
- 通过真实 HTTP 上传工具导出格式的 CSV，确认不再出现 `[Errno 22]`。

## 完成标准

- 复现用例不再返回文件读取错误。
- 筛选任务能够创建并完成无 AI 条件的最小流程。
- 全部自动化测试通过。
- 本地浏览器服务继续在 `http://127.0.0.1:5000/` 可用。
